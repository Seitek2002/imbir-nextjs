# Статус интеграции с API

> Дата: 2026-06-30 · Источник: Swagger `https://imbir.sino0on.ru/api/schema/` (72 эндпоинта)
>
> Кратко: **API-слой (`src/shared/api`) реализован полностью** — у всех 72 эндпоинтов
> есть request-функции. Большинство ключевых флоу подключены к UI. Ниже — что
> осталось подключить, чего не хватает на бэке и какие вопросы по контракту.

---

## 1. Полностью подключено и работает

- **Auth**: login, register (client/doctor/clinic), refresh, **logout** (подключён в этой сессии).
- **Каталог**: врачи, клиники, услуги (список + детально), блог (список + статья).
- **Пациент**: профиль (get/update + загрузка фото), история записей (список + **отмена**),
  избранное (список + добавление + **снятие**), отзывы (список).
- **Запись**: `createAppointment` с `is_online` и ссылкой Google Meet.
- **Кабинет врача**: профиль (get/update), записи, пациенты, услуги (CRUD), отзывы (через общий `getReviews`).
- **Кабинет клиники**: профиль (get/update), врачи (список + открепление), инвайты (CRUD), услуги (CRUD).
- **Чат**: комнаты, сообщения, WebSocket; ИИ-чат.
- **Upload**: `uploadFile` (используется для фото профиля).

## 5. Вопросы к бэку по контракту

1. **`POST /api/reviews/`** — в теле нет `target_id`. Как сервер понимает, к какому
   врачу/клинике/услуге относится отзыв? Сейчас `createReview` не может указать цель —
   поэтому создание отзывов нигде не подключено.
2. **References vs формы** — справочники отдают имена (`"Бишкек"`), а формы хранят слаги
   (`"bishkek"`). Что принимают эндпоинты регистрации?
3. **Загрузка файлов в регистрации** — формы врача/клиники передают `photo`/`documents`
   напрямую (`data.photo`, `data.certificates`). Эндпоинты регистрации принимают
   base64/data-URL, или фронт должен сначала вызвать `uploadFile` и слать URL?

## 6. Состояние форм

- ✅ **Подключены, с валидацией и обработкой ошибок**: login, регистрация
  (client/doctor/clinic — ошибки API показываются через toast), профиль `my-data`
  (обновление + загрузка фото), кабинет врача `my-data`, профиль клиники, услуги врача,
  оформление записи.
- ⚠️ **Регистрация**: дропдауны справочников захардкожены (см. §2); шаг 6 врача
  (оборудование/условия/оплата) отправляется пустым; проверить загрузку файлов (см. §5.3).
- ❌ **forgot-password**: нет бэка (см. §3).

## 7. Подключено в этой сессии

- Чат U2U + ИИ-чат на JWT, Google Meet в записи.
- Реальный `createAppointment` в форме записи (был стаб).
- Отмена записи → `cancelAppointment`; снятие из сохранённого → `removeFavorite`.
- Logout → `logoutFn` (через `useLogout`; заодно починен баг — кабинеты клиники/врача
  раньше не чистили авторизацию при выходе).
- Удалён мёртвый код (`MOCK_*`), клиентский CRUD специалистов клиники приведён к модели бэка.

### Из PR #12 (profile-fix), портировано на актуальную FSD-структуру

- **Аватар пациента**: загрузка через бинарный `avatar_upload` (multipart) в `PUT /api/profile/`
  и показ в сайдбаре. Прошлый путь `uploadFile → URL` фактически не сохранял аватар —
  у профиля нет поля URL, только `avatar_upload` (подтверждено по схеме).
- **ИИ-триаж с главной**: поле симптома в hero → `/chat?ask=` → ИИ-ассистент отправляет
  вопрос автоматически.
- **Header**: иконка чата ведёт на `/chat` для авторизованных; тексты ролей в регистрации.
- **Проверено по схеме**: `GET /api/profile/favorites/` отдаёт **массив**, а не пагинацию —
  поэтому изменение из PR (`data.data`) НЕ внесено (оно бы сломало избранное).
- **Не взято** (регресс/дубль): откат чата на прототип `:8054`, переразводка `src/views/*`
  (уже сделана на master в FSD), `skipHydration` (риск гонки токена), `http`-паттерн картинок.
