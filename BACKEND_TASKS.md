# Задачи для бэкенда (контракт от фронта)

> Фронт ведущий — структуры ниже это то, что фронт ждёт. Сделайте так, и экраны
> подключатся без правок логики. Вопросов нет, есть требования. Если что-то
> технически нельзя — скажите, обсудим.
>
> Базовый тип отзыва (как фронт его уже читает):
> ```ts
> ReviewItem = { id, author: {id, full_name}, target_type: "doctor"|"clinic"|"service",
>                rating: number, text: string, created_at: string }
> ```

---

## 1. Отзывы: создание с указанием цели — БЛОКЕР

**Зачем.** Сейчас отзыв создать нельзя: в `POST /api/reviews/` нет поля, к кому он.
Блокирует «оставить отзыв» на враче/клинике/услуге и из истории записей.

**Требование.** Принимать `target_id` в теле.

```jsonc
POST /api/reviews/
{ "target_type": "doctor", "target_id": 12, "rating": 5, "text": "Отличный врач" }

// 201:
{ "id": 42, "author": { "id": 1, "full_name": "Иван И." },
  "target_type": "doctor", "target_id": 12, "rating": 5,
  "text": "Отличный врач", "created_at": "2026-06-30T10:00:00Z" }
```
Желательно вернуть `target_id` и в ответе (для кэша на фронте).

---

## 2. Отзывы: редактирование

**Зачем.** На `/profile/reviews` есть «Редактировать» — сейчас правка только локальная.

```jsonc
PUT /api/reviews/{id}/
{ "rating": 4, "text": "Обновлённый текст" }
// 200: { ...ReviewItem }   // только автор; чужой → 403
```

---

## 3. Отзывы: удаление

**Зачем.** На `/profile/reviews` есть «Удалить» — сейчас удаляется только локально.

```jsonc
DELETE /api/reviews/{id}/
// 204 No Content            // только автор; чужой → 403
```

---

## 4. Ответ на отзыв (врач / клиника)

**Зачем.** На `/doctor/reviews` есть форма ответа — текст сейчас никуда не уходит.

```jsonc
POST /api/reviews/{id}/reply/
{ "text": "Спасибо за отзыв!" }
// 200: { ...ReviewItem }    // отвечает владелец цели (врач/клиника); повторный вызов = правка ответа
```

И добавить во **все** ответы отзывов поле `reply`:
```jsonc
"reply": { "text": "Спасибо за отзыв!", "created_at": "2026-06-30T11:00:00Z" } | null
```

## 5. Восстановление пароля

**Зачем.** Страница `/forgot-password` существует, но эндпоинта нет.

```jsonc
POST /api/auth/password-reset/
{ "email": "user@mail.com" }
// 200 всегда (не раскрывать, существует ли email)

POST /api/auth/password-reset/confirm/
{ "token": "<из письма>", "password": "новый_пароль" }
// 200 | 400 (невалидный/истёкший токен)
```
Уточните канал доставки токена (email или SMS) — подстроим UI.

## 6. Загрузка файлов в регистрации — принимать URL

**Решение фронта.** Перед регистрацией фронт сам загрузит файлы через `POST /api/upload/`
и пришлёт **строки-URL** (как уже делает профиль пациента).

**Требование.** Регистрация врача/клиники и обновление профилей принимают URL-строки
(не base64) в полях:
- врач: `step1.photo`, `step4.documents[]`
- клиника: `logo`, `photos[]`, `documents[]`

```jsonc
// пример внутри POST /api/auth/register/doctor/
"step1": { "photo": "https://imbir.sino0on.ru/media/uploads/ab12.jpg", ... }
```
Если регистрация сейчас ждёт base64 — переключите на строку-URL.

---

## 7. Справочники — принимать имена

**Решение фронта.** Фронт будет хранить и отправлять **имена** из `/api/references/*`
(а не слаги). Напр. `city: "Бишкек"`, `clinic_type: "Частная"`, `languages: ["Русский"]`.

**Требование.** Регистрация и фильтры (`/api/doctors/`, `/api/clinics/`, …) принимают
ровно те же строки, что отдают справочники. Если где-то нужен ID/слаг — скажите,
тогда справочники должны отдавать объекты `{ "value": "...", "label": "..." }`,
и мы будем слать `value`.

## 8. (опционально) Получение одной записи — для статуса оплаты

**Зачем.** На экране оформления записи есть «Проверить статус» — сейчас заглушка.
Чтобы опрашивать статус, нужен GET одной записи (в Swagger только POST/PATCH).

```jsonc
GET /api/appointments/{id}/
// 200: { "id": 55, "status": "pending"|"confirmed"|..., "is_online": true,
//        "google_meet_link": "https://meet.google.com/...", ... }
```
Не срочно — пока платежей нет.
